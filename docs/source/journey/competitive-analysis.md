竞品分析与需求提炼
==================

原始需求
--------

我们团队需要一个企业内部的 LLM API 网关。在决定自研之前，我们评估了市面上的主要方案。

核心需求提炼
-----------

通过 .omx 目录中保存的深度访谈记录和上下文文档，我们提炼出了以下**不可妥协**的需求：

1. **工号验证的自助注册** -- 用户用工号自助注册，不需要管理员手动创建账号
2. **按模型的 IP 白名单** -- 敏感模型只允许特定网段访问（如仅内网或特定 VPN）
3. **前缀索引 + SHA-256 的 API Key** -- 安全的密钥管理，不存明文
4. **团队级 RBAC** -- 通过团队批量管理模型访问权限
5. **全链路审计** -- 每个请求留痕，无论成功还是失败
6. **轻量部署** -- 不需要一堆外部依赖就能跑起来
7. **管理控制台** -- 运营人员不需要 CLI

竞品分析
--------

### NewAPI（one-api / new-api）

NewAPI 是一个 Go + React 编写的 LLM API 网关，主要面向中国市场。它的定位是"把各种 LLM 提供商统一转成 OpenAI 格式"。

**优势：**

- 部署简单 -- 单个 Docker 容器，默认 SQLite，零外部依赖
- 支持多种数据库 -- SQLite、MySQL、PostgreSQL
- 集成了 Midjourney、Suno 等创意 AI 工具
- 中文界面友好

**不满足我们需求的地方：**

| 我们的需求 | NewAPI 现状 |
|-----------|------------|
| 工号验证自助注册 | 仅有开放注册和 Telegram 登录，无企业身份验证 |
| 按模型 IP 白名单 | 无 IP 访问控制 |
| SHA-256 哈希密钥 | 无文档化的密钥安全机制 |
| 团队级 RBAC | 仅基础的 admin/user 区分 |
| 全链路审计 | 无审计日志 |
| 轻量部署 | 这一点满足 |

**核心问题：功能太多但安全能力不足。**

NewAPI 集成了在线支付（易支付）、Telegram 登录、Midjourney 代理等面向 C 端用户的功能，
但缺少我们需要的所有企业安全特性。它的复杂性花在了错误的地方。

### LiteLLM Proxy（UI 版）

LiteLLM Proxy 是一个 Python 编写的 AI 网关，支持 100+ LLM 提供商，
有 Web 管理界面。被 Stripe、Netflix 等公司使用。

**优势：**

- 提供商覆盖最广 -- 100+ LLM 提供商
- 企业级安全 -- SSO、JWT、IP ACL、审计日志（但仅限付费版）
- 丰富的 RBAC -- 团队/组织/角色层级
- 内容安全 -- Secret 检测、LLM Guard、Llama Guard
- 密钥生命周期管理 -- 自动轮换、预算控制

**不满足我们需求的地方：**

| 我们的需求 | LiteLLM 现状 |
|-----------|-------------|
| 工号验证自助注册 | 不支持自助注册，必须管理员预创建用户 |
| 按模型 IP 白名单 | 仅付费企业版支持，且文档不公开 |
| 轻量部署 | 强制依赖 PostgreSQL，无 SQLite 模式 |
| 免费使用完整功能 | 核心安全特性（SSO、IP ACL、审计）全部付费 |

**核心问题：东西太多，但该有的没有。**

LiteLLM 的配置极其复杂（仅 JWT 认证就有几十个配置项），
但连一个合理的用户自助注册系统都没做好。
用户不能自助注册，要么管理员手动创建，要么通过 SSO 自动添加。
对于我们的场景（内部团队快速上线），这增加了不必要的运维负担。

此外，我们需要的 IP 白名单、审计日志等企业功能全部在付费墙后面。

自研决策
--------

基于以上分析，我们做出了自研决策：

- **不做 NewAPI 那样的功能堆砌** -- 不集成支付、不集成 Telegram 登录、不代理 Midjourney
- **不做 LiteLLM 那样的配置爆炸** -- 保持简洁的配置面，用合理的默认值
- **聚焦我们的 7 个核心需求** -- 每个功能都是我们自己要用的
- **保持轻量** -- PostgreSQL + Redis 足够，不需要更多外部依赖
- **安全内置** -- 哈希密钥、审计日志、IP 白名单全部开源可用，不设付费墙

这个决策让我们在 5 天内从零到完整交付，且每一行代码都服务于实际需求。
